## ГЛАВА 1 ОПИСАНИЕ ПРЕДМЕТНОЙ ОБЛАСТИ

### 1.1. Анализ предметной области кафе и существующих систем бронирования

Прежде чем разрабатывать приложение, имеет смысл посмотреть, как устроено бронирование столов в реальных кафе. Это поможет понять, какие функции действительно нужны.

В типичном кафе есть залы (основной зал, веранда) и столы разной вместимости. Гость хочет прийти в определённое время и быть уверенным, что стол свободен. Администратору нужно видеть, какие брони есть сегодня и на неделю, чтобы распределять нагрузку на персонал.

На рынке есть сервисы вроде OpenTable, Forkly и BookingTable. У них есть свои плюсы и минусы:

Плюсы:
- Удобный онлайн-поиск свободных столов.
- Возможность бронировать в любое время без звонка.
- Система лояльности для постоянных гостей.

Минусы:
- Многие сервисы платные или требуют подключения кафе к своей платформе.
- Сложный интерфейс для маленьких кафе.
- Нет интеграции с белорусскими реалиями.

Что это значит для моей работы? Посмотрев на существующие сервисы, я понял, что для моего курсового проекта не нужно делать «всё сразу». Гораздо важнее сделать стабильное и понятное приложение.

Поэтому в своём курсовом проекте я сделаю акцент:
- **Простота.** Интерфейс чистый и минималистичный.
- **Базовый функционал.** Самое главное: просмотр столов, бронирование, личный кабинет и админка.
- **Надёжная проверка.** Сервер сам проверяет, не занят ли стол.
- **Обязательная авторизация.** Бронировать могут только зарегистрированные пользователи.
- **Администрирование.** Отдельная панель для управления бронями.
- **Лояльность.** Постоянные гости получают бонусные баллы.

### 1.2. Технологии разработки

**Java и Spring Boot.** Java – популярный язык для серверной разработки. Spring Boot – фреймворк для быстрого создания веб-сервера. Он настраивает Tomcat, подключает базу данных, валидирует запросы.

**Spring Data JPA / Hibernate.** ORM-система для доступа к СУБД. Позволяет работать с базой через Java-объекты. Схема БД создаётся автоматически при запуске.

**JWT (JSON Web Token).** Способ авторизации без сессий. Сервер создаёт токен с данными пользователя, подписанный секретным ключом. Фронт хранит токен и шлёт с каждым запросом.

**H2 Database.** Встроенная реляционная база данных. Не требует установки, запускается вместе с приложением.

**REST API.** Server предоставляет эндпоинты для работы с данными. Фронт делает HTTP-запросы и получает JSON.

**Vue 3 + TypeScript.** Фреймворк для создания пользовательского интерфейса. Выбран за простоту и Composition API. TypeScript добавляет статическую типизацию.

**Tailwind CSS.** CSS-фреймворк с готовыми классами. Позволяет быстро верстать без лишних файлов стилей.

**Pinia.** Хранилище состояния для хранения токена и данных пользователя.

**Vite.** Сборщик проектов. Быстрый запуск и горячая перезагрузка.

Благодаря выбранному стеку достигается разделение ответственности: сервер отвечает за данные и бизнес-логику, клиент – за интерфейс.

### 1.3. Интеграция API и взаимодействие клиента с сервером

Фронт на Vite (порт 5173) и бэкенд на Spring Boot (порт 8080) работают на разных портах. Из-за политики CORS браузер не может обращаться к разным портам напрямую, поэтому используется прокси: Vite-сервер пересылает запросы с `/api/...` на бэкенд.

### 1.4. Требования к веб-приложению

Перед началом разработки определены функциональные и нефункциональные требования.

**Функциональные требования (что приложение делает):**
- Регистрация и авторизация пользователей.
- Просмотр залов и столов.
- Поиск свободных столов на выбранную дату и время.
- Бронирование стола.
- Отмена брони.
- Личный кабинет с историей бронирований и QR-кодом.
- Администрирование: просмотр всех броней, смена статусов, начисление бонусов.
- Разграничение ролей: гость и администратор.

**Нефункциональные требования (как приложение делает):**
- Простота. Минималистичный интерфейс.
- Скорость. Быстрый отклик.
- Надёжность. Сервер проверяет конфликты броней.
- Безопасность. Пароли хранятся в хэшированном виде (BCrypt), доступ по JWT.

Согласно общим требованиям ТЗ, приложение представляет собой клиент-серверную систему: серверный REST API на Java (Spring Boot) с реляционной базой данных, и клиентское SPA-приложение на Vue 3. Настройки меняются в файле application.properties без изменения исходного кода.

**Что решено не делать (сознательно):**

## ГЛАВА 4 ИНФОРМАЦИОННАЯ МОДЕЛЬ СИСТЕМЫ И ЕЁ ОПИСАНИЕ

### 4.1. Логическая модель данных

На основе функциональной модели разработана информационная модель системы. Выделены следующие сущности:

1. **User (пользователь)** – id, имя, фамилия, телефон (уникальный), хэш пароля (BCrypt), роль (GUEST / ADMIN), бонусные баллы.
2. **Hall (зал)** – id, название, описание.
3. **RestaurantTable (стол)** – id, зал (FK → Hall), номер стола, вместимость, локация.
4. **Booking (бронь)** – id, гость (FK → User), стол (FK → RestaurantTable), время начала, время конца, количество гостей, комментарий, статус (NEW / CONFIRMED / COMPLETED / CANCELLED / NO_SHOW), QR-код (UUID).

Связи:
- Hall 1 → ∞ RestaurantTable (зал содержит несколько столов).
- User 1 → ∞ Booking (гость создаёт несколько броней).
- RestaurantTable 1 → ∞ Booking (стол может быть забронирован несколько раз в разное время).

[СКРИНШОТ 4.1 – Таблицы базы данных в H2 Console]

### 4.2. Приведение к 3-й нормальной форме (3НФ)

Все таблицы приведены к третьей нормальной форме:

- **1НФ:** Каждый столбец содержит атомарные значения (нет списков, массивов или вложенных объектов). Все строки уникальны по первичному ключу.
- **2НФ:** Каждый неключевой атрибут функционально полно зависит от первичного ключа. Например, userName зависит от booking.id? Нет, userName зависит от user.id, поэтому все поля пользователя вынесены в отдельную таблицу.
- **3НФ:** Каждый неключевой атрибут нетранзитивно зависит от первичного ключа. Нет атрибутов, зависящих от других неключевых атрибутов.

Доказательство:
- В таблице Bookings внешние ключи user_id и table_id ссылаются на первичные ключи таблиц Users и Tables соответственно. Через них можно получить имя пользователя, номер стола, название зала.
- В таблице Tables внешний ключ hall_id ссылается на первичный ключ таблицы Halls. Название зала хранится только в таблице Halls, исключая дублирование.

## ГЛАВА 5 ОБОСНОВАНИЕ ОРИГИНАЛЬНЫХ РЕШЕНИЙ ПО ИСПОЛЬЗОВАНИЮ ТЕХНИЧЕСКИХ И ПРОГРАММНЫХ СРЕДСТВ

В процессе разработки принят ряд решений, не являющихся обязательными по ТЗ:

1. **Встроенная СУБД H2.** Выбрана вместо PostgreSQL для упрощения развёртывания. При запуске создаётся файл базы данных, не требуется установка сервера. Замена на PostgreSQL выполняется изменением одной строки в application.properties.
2. **JWT вместо сессий.** Бессессионная аутентификация упрощает масштабирование и не требует хранения состояния на сервере.
3. **Проверка конфликтов броней на сервере.** Бизнес-логика проверки пересечений времени выполняется на сервере в методе BookingService, исключая двойное бронирование.
4. **Автоматическая генерация схемы БД (spring.jpa.hibernate.ddl-auto=update).** Hibernate сам создаёт таблицы при старте на основе Java-сущностей.
5. **Клиентская часть на Vue 3 для демонстрации API.** Позволяет наглядно показать работу сервера, не требуется для работы API.

Данные решения позволили уложиться в сроки курсового проекта и обеспечить стабильную работу системы.

## ГЛАВА 6 ОПИСАНИЕ АЛГОРИТМОВ, РЕАЛИЗУЮЩИХ БИЗНЕС-ЛОГИКУ

### 6.1. Алгоритм авторизации

1. Пользователь отправляет POST /api/auth/register или POST /api/auth/login.
2. Сервер принимает JSON (имя, телефон, пароль для регистрации; телефон и пароль для входа).
3. Для регистрации: проверка уникальности телефона, хэширование пароля BCrypt, сохранение в БД.
4. Для входа: поиск по телефону в БД, проверка пароля через BCrypt.matches().
5. Если всё ок – генерация JWT-токена (содержит телефон и роль, подписан секретным ключом, срок 24 часа).
6. Ответ: { token, user }.

### 6.2. Алгоритм поиска свободных столов

1. Фронт отправляет GET /api/tables/available?date=...&start=...&end=...&guests=... .
2. Сервер получает все столы, вмещающие указанное количество гостей (restaurantTableRepository.findByCapacityGreaterThanEqual(guests)).
3. Для каждого стола выполняется запрос к bookingRepository: найти брони, пересекающиеся с [start, end].
4. Если пересечения нет – стол считается свободным.
5. Список свободных столов возвращается в JSON.

Условие пересечения: (old.startTime < new.endTime AND old.endTime > new.startTime).

### 6.3. Алгоритм бронирования

1. Фронт отправляет POST /api/bookings с JSON: tableId, startTime, endTime, guestsCount, comment.
2. Сервер проверяет: стол существует; время не в прошлом; endTime > startTime; гости не превышают вместимость.
3. Сервер проверяет пересечения с существующими бронями (тот же запрос, что в 6.2, но для одного стола).
4. Если пересечение найдено – 400 «Стол уже занят».
5. Если всё свободно – создаётся бронь: статус NEW, qrCode = UUID.randomUUID(), createdAt = now.
6. Бронь сохраняется в БД, возвращается BookingDto.

### 6.4. Алгоритм администрирования

1. Администратор отправляет PATCH /api/admin/bookings/{id}/status с JSON: { status: "CONFIRMED" | "COMPLETED" | "NO_SHOW" | "CANCELLED" }.
2. Сервер находит бронь по id.
3. Проверяет допустимость перехода (из NEW в CONFIRMED, из CONFIRMED в COMPLETED/NO_SHOW и т.д.).
4. Если новый статус COMPLETED – начисляет пользователю +50 бонусных баллов (user.bonusPoints += 50).
5. Бронь сохраняется с новым статусом.
6. Возвращается обновлённый BookingDto.

### 6.5. Параллельная обработка

Spring Boot использует многопоточный Tomcat, каждый запрос обрабатывается в отдельном потоке. Конфликты при одновременном бронировании предотвращаются за счёт атомарности транзакций (@Transactional).

## ЗАКЛЮЧЕНИЕ

Итог работы: цель выполнена, разработано серверное приложение (REST API) для управления кафе с возможностью бронирования. Приложение включает серверную часть на Java Spring Boot (REST API, JWT, H2) и клиентскую часть на Vue 3.

Приложение позволяет пользователям регистрироваться, просматривать залы и столы, искать свободные столы на выбранное время, бронировать и отменять брони. Администратор управляет всеми бронями, меняет статусы и начисляет бонусы.

Работа началась с анализа предметной области. Согласно ТЗ, разработана функциональная модель IDEF0 и информационная модель, приведённая к 3НФ. Библиотека Spring Data JPA автоматически генерирует схему БД по Java-классам.

Стек выбран по требованиям дисциплины: Java Spring Boot для сервера, Vue 3 для клиента. Взаимодействие – REST API с JWT. Данные – H2, встроенная СУБД.

Проект проверен на всех сценариях, включая двойное бронирование и разграничение ролей. Задачи закрыты, требования выполнены.
